Arguments: $ARGUMENTS
The first argument is the site name. SITE = website-tests/<site name>/.
The optional second argument is a filter: a priority (High, Medium, Low), a mode (LoggedOut or LoggedIn, matching the [LOGGED OUT] / [LOGGED IN] tag at the start of the title; old tags: [GUEST] and no tag = LoggedOut, [PLAYER] = LoggedIn; Guest and Player also work as filter names), Changes (only the cases with Changes account = Yes), or a list of TC IDs.
**Payment-invalid mode:** if the second argument is `payment-invalid`, this run is not a normal run. It runs ONLY the payment cases (Sub-type starts with "Payment", Approved = Skip or Yes, never No) with a made-up INVALID card in the real payment window, one attempt each, to see what error the window shows. It needs the site's "Allowed invalid-card check" section with status ON and a named person in approved-by (see .claude/rules/opt-in.md, section 4). No normal case is run in this mode, and a normal run (no `payment-invalid`) never types a card. Where a step below says "(payment-invalid)" it applies only in this mode.
**Payment-human mode:** if the second argument is `payment-human`, this run is not a normal run and Steps 1 to 3 do not apply: follow the section "Payment-human mode" at the end of this file, then Steps 4 and 5. A PERSON types the card in the open Chrome window and clicks "Pay"; the agent types nothing and never sees the values. It needs the site's "Allowed person-typed card check" section with status ON and a named person (see .claude/rules/opt-in.md, section 5).
**Payment check after a full run:** a full run (no filter) always runs Step 6, the payment check, right after the last batch of Step 3, which starts by itself. **A full run makes ONE run folder and ONE report:** the payment check writes into the same RUN, its results replace the "Skipped (payment)" ones, and Steps 4 and 5 run once, after Step 6, so report.html shows every normal case and every payment result together. A new user only types `/test-website <link> <site> userid=...` and "proceed", then types the card in Chrome when told to. There is no option to leave it out: the person can answer "Skip" at the card step, and nothing is paid.
**Chrome stays hidden:** every test runs in a hidden (headless) Chrome, so no window pops up while you work. Only a payment case where a person types the card opens a visible Chrome window, and only when it is that person's turn.
**Alerts:** a project hook (.claude/settings.json) plays a short chime twice ("ting ting") whenever Claude Code asks the person something (AskUserQuestion) or needs a permission, and at no other time. So whenever the run needs the person to answer or do something (including "Type the card details…"), ask through AskUserQuestion. Do not run notify_person.py yourself and do not send PushNotification for progress: that would chime when nothing is needed, or twice.
PROJECT = the project folder (absolute path). EVIDENCE SCRIPT = PROJECT/.claude/scripts/test_evidence.py.

## Step 1: Load the approved tests
Use python3 with openpyxl to read SITE/testcases.xlsx and take only rows where Approved is Yes, then apply the filter. **(payment-invalid)** Take instead only the rows whose Sub-type starts with "Payment" and whose Approved is Skip or Yes (leave out No). Read SITE/settings.md "Allowed invalid-card check": if it is missing, its status is not ON, approved-by is empty or still the template text, or a field you need is not listed, or SITE/settings.card.local.md (the INVALID values, git-ignored) is missing, STOP and tell me what to fix (I switch it ON by typing my name; never switch it ON yourself). In this mode ignore the next sentence about Skip rows. **Payment cases are never run by a normal run** (only the payment check in Step 6 runs them): leave out every row whose Approved is Skip and every row whose Sub-type starts with "Payment" (even when Approved is Yes). Step 2 writes a "Skipped (payment)" result for them and nothing else; no browser is opened for them.
If there are none to run, stop and tell me.
Read SITE/settings.md: the "Login (LOGGED IN mode)" section, "Allowed when LOGGED IN", "Allowed when LOGGED OUT", "Never", and the opt-in sections "Allowed to type", "Allowed cart actions" and "Allowed demo checkout" if present (see .claude/rules/opt-in.md). The website-tester agent needs these.
Also read SITE/settings.local.md (ignored by git). It holds the real test-account values, for example `- TEST_USER_ID: <id>`, for the placeholders such as {TEST_USER_ID} in settings.md and in the Start URLs and Steps. If an approved [LOGGED IN] case uses a placeholder whose value is missing, stop and ask me for it.
Check that Pillow is installed (python3 -c "import PIL"). If it is missing, run: pip3 install --user pillow
Safety check before running (never skipped by /run-tests, whatever the arguments or the site): read the Steps of every approved case. **(payment-invalid)** The payment cases may click the item's Buy button, close the payment window, type only the four listed INVALID values ({CARD_NUMBER}, {CARD_EXPIRY}, {CARD_CVC}, {CARD_EMAIL}) and click "Pay" once, as the "Allowed invalid-card check" section lists them. A step that types anything else, uses a real or valid card, or clicks anything else in the payment window is refused like any other: do NOT run that case and list it for me. If any action step clicks or presses something that pays or purchases (a button with a real-money price, Buy, Purchase, Pay, Checkout, Add to cart, the final button of the gift flow) or anything in the "Never" list of settings.md, do NOT run that case. List it for me with the TC ID and the step, and run the rest. Claim, spending loyalty points and Logout are allowed if settings.md allows them. If one of these allowed clicks opens a payment window or asks for real money while the test runs, the website-tester stops and marks that test FAILED. A step that types, changes the cart or checks out may run only if the matching opt-in section has status ON and lists that exact field, value or button; otherwise do NOT run that case and list it for me.

## Step 2: Make the run folder
RUN = SITE/runs/<YYYY-MM-DD_HHMM>/ (absolute path) with a subfolder results/ and one evidence folder per test: RUN/<TC ID>/ (for example RUN/TC-001/).
Write RUN/run_timing.json: {"started": "<now, ISO 8601 local time, from `date +%Y-%m-%dT%H:%M:%S`>", "coordinator_model": "<your model>", "tester_model": "<the website-tester model and effort>", "batches": [], "refused": [<one {"tc": "<TC ID>", "step": <step number>, "reason": "<why>"} for every case the safety check in Step 1 did not run>]}. The reports use it to show the full run time split into coordinator and website-tester time; the eval script uses "refused".
**(payment-invalid)** Skip this paragraph in payment-invalid mode: the payment cases are run, not skipped. Otherwise write the skipped payment results: python3 "<PROJECT>/.claude/scripts/skip_payment_cases.py" "<RUN>" "<SITE absolute path>" [the filter argument, if one was given]. It writes RUN/results/<TC ID>.json (status SKIPPED, skip_kind "payment") for every payment case, opens no browser and clicks nothing. If it prints a WARNING (a payment case with Approved = Yes), show it to me in Step 5. These cases are not "refused" in run_timing.json.

## Step 3: Run the tests
**(payment-invalid)** Run the payment cases in ONE batch, one after another: first the case that does not type a card (the one that only opens and closes the window), then the others. Give the agent the line `PAYMENT-INVALID MODE` and the whole "Allowed invalid-card check" section as text (placeholders only). **Never paste the INVALID values into the prompt, and never print them to me:** the agent reads SITE/settings.card.local.md itself. Nothing is captured while the card form is filled: the agent starts no recorder and no trace, takes no screenshot or snapshot of the filled form, and uses the withheld-image script for those steps (see .claude/agents/website-tester.md). So for these tests `_screen.mp4` and `_trace.zip` are NOT expected: do not look for them and do not run the recorder stop command for them. After the batch, check each result JSON has `card_check` (rejected, accepted, window_only or unclear) and `card_error`; if one is missing, say so in Step 5. If any result says `accepted`, stop and tell me at once. Skip the ordering rule below.
Order the tests: first [LOGGED OUT], then [LOGGED IN] with Changes account = No, then [LOGGED IN] with Changes account = Yes. This way a claim or a spend does not change what the look-only tests see.
Split the tests into batches of 5, keeping that order. For each batch, start one **website-tester** agent (Agent tool, subagent_type "website-tester"; its rules are in .claude/agents/website-tester.md). Run the batches one after another, never at the same time.
Give each agent: the test cases of its batch (TC ID, Title, Area, Priority, Platform, Start URL, Steps, Expected answers, Changes account), the RUN path, the PROJECT path, the EVIDENCE SCRIPT path, the RECORDER SCRIPT path (PROJECT/.claude/scripts/browser_recorder.py), the settings.md sections listed in Step 1 (paste them as text), and the placeholder values from SITE/settings.local.md (for example "{TEST_USER_ID} = <id>"). Pass the test cases with their placeholders as they are.
The agent replies with one line per test: TC ID | status | duration | short reason.
After each batch, check that RUN/results/<TC ID>.json, the screenshots, the replay video (or, if it says "mp4 skipped", the replay GIF) and the trace zip exist for every test in it (the screen recording <TC ID>_screen.mp4 is expected too, unless the agent said recording was not available or "screen video skipped"; a missing one is noted in Step 5, not a reason to re-run). Also check that no recorder Chrome is left open: `pgrep -f webtest-chrome-` should print nothing; if it does, run `python3 "<PROJECT>/.claude/scripts/browser_recorder.py" stop "<RUN>" "<TC ID>"` for each test of the batch, and add the batch to "batches" in RUN/run_timing.json: {"batch": <n>, "tests": [<TC IDs>], "agent_sec": <agent duration in seconds>, "tokens": <agent tokens>, "tool_calls": <agent tool uses>}, taken from the usage the agent run reports when it finishes.
If a test comes back BLOCKED or needs confirmation, do not re-run it or work around it: keep it as it is and list it in Step 5.
A SKIPPED test (its precondition was not met, for example the reward was already claimed) is not re-run either.
**Full run (no filter):** after the last batch, go to Step 6 (the payment check) now, in the same RUN, and only then do Steps 4 and 5. With a filter there is no Step 6: go on to Step 4.
If the website-tester agent is not available, use a general-purpose agent and paste the whole content of .claude/agents/website-tester.md into its prompt.

## Step 4: Make the reports
Set "finished" in RUN/run_timing.json to the current time (`date +%Y-%m-%dT%H:%M:%S`).
First take the real test-account values out of the results: python3 "<PROJECT>/.claude/scripts/scrub_secrets.py" "<SITE absolute path>" "<RUN>/results"
Work out what the website-tester agents cost: python3 "<PROJECT>/.claude/scripts/run_cost.py" "<RUN>". It finds the agent transcripts that name RUN, prices them per model and writes "cost" into RUN/run_timing.json; the reports show it. If it finds no transcripts, say so and continue.
Run: python3 "<PROJECT>/.claude/scripts/build_run_report.py" "<RUN>" "<SITE absolute path>" "<site name>"
It creates from RUN/results/*.json:
1. RUN/report.html (layout from .claude/scripts/report_html.py): an Overview with totals, the pass rate by category (Functional / Non-functional, from the Test category column of testcases.xlsx), mode and priority, a "Needs attention" table of tests that did not pass, the changes to the test account and a table of all tests; a sidebar with search and status, mode, priority and category filters; then one page per test that starts with what went wrong (the failed step, expected and actual answer, and its screenshot), then account changes, links to its evidence folder, steps PDF and trace zip, the screen recording (when there is one), the replay video of the step screenshots (the GIF for older runs), and every step with expected answer, answer, what was seen and a screenshot. Failed steps are shown in red. A note explains the screen recording, the replay video and the trace zip.
2. RUN/results.xlsx: sheets "Summary", "Results" and "Steps".
3. RUN/results.csv: the Results sheet as UTF-8 with BOM.
It also fills "Last result" and "Last run" in SITE/testcases.xlsx. Then run python3 "<PROJECT>/.claude/scripts/scrub_secrets.py" "<SITE absolute path>" --check; it must say "found 0 in total". If it prints TESTCASES_OPEN, the file is open in Excel: ask me to close it, then run the script again.

## Payment-human mode (`/run-tests <site> payment-human`)
A person types the card and clicks "Pay" in the open Chrome window. The agent never types in the payment window, never clicks "Pay" and never sees the values. No normal case is run in this mode.
**H1. Load and check.** Read SITE/testcases.xlsx: only the rows whose Sub-type starts with "Payment" and whose Approved is Skip or Yes (never No). Read SITE/settings.md "Allowed person-typed card check". STOP and tell me what to fix if: the section is missing, its status is not ON, approved-by is empty or still the template text, or `items` does not list the item of a case with its maximum price (a person switches it ON in settings.md, or Step 6 records their "proceed" as the approval; never switch it ON in any other way, and never with a made-up name). Also STOP if the wdio-mcp tools are not available (load them with ToolSearch), or if PROJECT/.claude/settings.json does not contain "card_guard.py". Cases with Sub-type "Payment login prompt (skip)" also need "Allowed logged-out price click" ON with a named approver: if it is not, do not run them (do not stop the others) and list them for me as refused, with what to switch on.
**H2. Real card, confirmed once.** A real card is the normal case. If the section says `real: NOT ALLOWED` (or has no `real:` line), STOP before opening any payment window and tell me the one line to change in settings.md (`- real: ALLOWED`, with my name and the date in approved-by); never write it yourself. With `real: ALLOWED`, ask ONE AskUserQuestion before the first payment window of the run: list every card-payment item with its maximum price from the section and the total, say that a real card really pays and that each one goes through only when I click Pay, and offer "Yes, use my real card for all of these" / "Use an invalid card (rehearsal, nothing can be paid)" / "Stop". If the section says `auto-pay: ALLOWED` with a `max-total-per-run` above 0, offer instead as the first option "Yes: I pay the first one, the agent pays the rest with my saved card (at most USD <max-total-per-run> in this run)". The run only uses AUTO-PAY when I chose that option. That answer covers every listed item for this run: do not ask again per item. Never ask me for card values and never print them.
**Spend ledger and budget (real card only).** Every real-card attempt is written to the tester's own spend ledger, so it can be found and refunded later, and nothing is opened that would go over the tester's budget. The ledger script is `python3 "<PROJECT>/.claude/scripts/spend_ledger.py"`; its files `PROJECT/spend/budget.md` (written only by a person) and `PROJECT/spend/ledger.csv` are ignored by git. Only the coordinator runs it, never the website-tester. Before the H2 question, run `spend_ledger.py list`, then `spend_ledger.py check <maximum>` for each card-payment item (the maximum from `items`). If it exits 2 (budget not set), tell me the file and its three lines to fill in (`card-limit`, `budget` below the card limit, `per-payment-cap`), never fill them yourself, and offer only "Use an invalid card" / "Stop". In the H2 question show the budget, the open spend and what is left, and list only the items whose check said OK; the refused ones (over the per-payment cap) are not run and keep "Skipped (payment)" with the reason "over the spend budget". With a real card, **before every Phase A (and every AUTO-PAY PREP) run `spend_ledger.py check <that item's maximum>` again**: if it does not print OK (earlier payments in this run used the budget), do not open the window: that case and the rest are not run ("over the spend budget"), and tell me what is left. **After every Phase C of a real-card case**, write the attempt: `spend_ledger.py add --site <site> --run "<RUN>" --tc <TC ID> --item "<item>" --amount <the price the window showed, from phase_a.json> --status <paid|declined|unclear> [--order-id <ID>] --message "<card_error>"`: `paid` for card_check "paid", `declined` for "rejected", `unclear` for "unclear" and "window_closed" (a closed window without a message may still have charged). No row for "skipped" and "timeout" (Pay was not clicked). The order ID comes from `order_id` in RUN/<TC ID>/phase_b.json (the tester reads it from the window's visible texts); if the case was paid and there is none, ask me once (AskUserQuestion, "Other") for the transaction or order number from the payment receipt email, and accept "none". Put the printed row ID (for example P-0003) into the result JSON as `ledger_id`. Never mark a refund yourself: `spend_ledger.py set <ID> --refund requested|confirmed` (and `--status hold|released`) only when I say so.
**H3. Make the run folder** as in Step 2 (RUN/results/ and RUN/<TC ID>/ for these cases) and RUN/run_timing.json with `"mode": "payment-human"` added. Do not run skip_payment_cases.py.
**H4. Test the card guard once, before any payment window is opened.** Run `python3 "<PROJECT>/.claude/scripts/card_guard.py" on "<RUN>" "<first TC ID>"`, then call the wdio-mcp `snapshot` tool. It MUST be refused with a message that starts "CARD GUARD". Then run `card_guard.py off`. If the call was not refused (it returned a page, or an error such as "no session"), the hook is not active (Claude Code must be started in the project folder; check /hooks): STOP, tell me, and open no payment window.
**H5. Run the cases** in two groups. What every website-tester agent gets: the case(s) (TC ID, Title, Area, Priority, Platform, Start URL, Steps, Expected answers, Changes account), RUN, PROJECT, EVIDENCE SCRIPT, the RECORDER SCRIPT path, the settings.md sections listed in Step 1, the whole "Allowed person-typed card check" and "Allowed logged-out price click" sections as text, and the placeholder values from SITE/settings.local.md.
**Group 1: cases with no step that starts with "A person"** ("Payment login prompt" cases, and window-only cases in older test files). Nobody types; they run in a hidden Chrome. First tell me in one line: "The agent now checks the price buttons by itself in a hidden Chrome: nothing to do for you yet." Then run them in batches of up to 5 (window-only cases first, then login-prompt cases), one **website-tester** agent per batch (Agent tool, subagent_type "website-tester"), one batch after another, with the line `PAYMENT-HUMAN MODE NO-HANDOFF`. Each agent replies with one line per test, including card_check. After each batch do f.
**Group 2: card-payment cases** (they have "A person" steps), one at a time:
- a. First tell me: "Next: <item>. Do not touch Chrome until I write 'Type the card details…'." Then start one website-tester agent with the line `PAYMENT-HUMAN MODE PHASE A` and the case (Phase A opens a visible Chrome window). It replies `READY | ...` or a normal result line (then there is no handoff: go to f). If the reply says card text was already visible before READY (someone typed early), switch the guard on at once (b), tell me, and ask (AskUserQuestion) whether to delete the cached screenshot files the agent names (in Claude Code's tool-results folder for this session) without opening them.
- b. On READY: run `card_guard.py on "<RUN>" "<TC ID>"`. Tell me in the chat (the AskUserQuestion below makes the chime): the case, the item and price the agent reported, and that the Chrome window is open. For the FIRST card case of the run: "Type your card details and email in the Chrome window once, tick the window's 'save card' option if it shows one, and click Pay once." For every later case: "Your saved card should already be selected: check it, type only what the window asks (for example the security code) and click Pay once. If the card is not saved, type it again." Always add: "Do not type card details in this chat. Do not close the payment window yourself. Note the exact message it shows after Pay." Then ask with AskUserQuestion (I type the exact message under "Other" when I can): "Paid: a success message was shown (and the card was saved)" / "Paid, but the card was not saved" / "Declined: an error was shown" / "Pay stayed disabled (error shown)" / "Skip this case: nothing is paid" ("The window expired" can be typed under "Other"). Then ask, or let me say under "Other", whether the window is still open or closed by itself. Wait for my answer however long it takes. Meanwhile never type, click or capture anything yourself. If I answer "closed by itself", ask once more: "Did you see a message before it closed?" with "No message" / "Yes (type the exact text under Other; never card details)".
- c. Phase B (guard ON), only when the window should still be open (answers "still open", "Pay stayed disabled", "Skip", "expired"): start a website-tester agent with the line `PAYMENT-HUMAN MODE PHASE B` and one line `ANSWER: DONE kind=<invalid|real>` (the kind from H2), `ANSWER: PAY_DISABLED kind=<…>`, `ANSWER: SKIP` or `ANSWER: EXPIRED`, with the same information as in a. If it cannot reach or close the window, ask me to close it myself with its close control (for Pay Station: the back arrow "Ludus", top left) and wait for my yes. - **AUTO-PAY** (only when I chose it in H2 and the section says `auto-pay: ALLOWED`): it starts after a case where I answered "Paid" and said the card was saved. For every later card-payment case, as long as the money paid in this run plus the item's maximum stays within `max-total-per-run`: (1) start a website-tester with `PAYMENT-HUMAN MODE AUTO-PAY PREP` (hidden Chrome, no `--show`; it does the steps up to the price click and replies `PREP READY | …`); (2) run `card_guard.py on "<RUN>" "<TC ID>" --autopay`; (3) start a website-tester with `PAYMENT-HUMAN MODE AUTO-PAY PAY` (it clicks the price button, reads item and price, clicks "Pay" once, reads the result messages, closes the window and replies `AUTOPAID | …`, `DECLINED | …` or `NEEDS PERSON | …`); (4) when it reports the window closed, run `card_guard.py off`; (5) Phase C as in e with `ANSWER: DONE kind=real` and the messages it read. Add what was paid to the run total. Ask me nothing for these cases. If a case replies `NEEDS PERSON` (no saved card, a security code, a one-time code or 3-D Secure, a price that differs, or an unclear result), stop AUTO-PAY: switch the guard off once the window is closed, tell me why, and run that case and the rest the normal way (a to e).
- d. **The coordinator switches the guard off, never the tester:** only when the window is closed (the Phase B reply says so, or I confirmed it), run `card_guard.py off` yourself.
- e. Phase C (guard OFF): start a website-tester agent with the line `PAYMENT-HUMAN MODE PHASE C` and the same ANSWER line (for "closed by itself": `ANSWER: CLOSED_ITSELF kind=<…> message="<the text I typed, or none>"`), with the same information as in a. It takes the store-page screenshots, reads the points, writes the result and replies with one line including card_check. If it replies `PAYSTATION STILL OPEN`, switch the guard on again, ask me to close the window, then switch it off and repeat e.
